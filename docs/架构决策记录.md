# 架构决策记录（ADR）

> 这份文档记录「为什么这么做」，而不是「怎么用」。
> 每个决策都写清：当时的约束、被否决的方案、以及付出的代价。
> 配套阅读：[本地化改造方案与评估.md](本地化改造方案与评估.md)（偏实现细节与平台能力清单）。

项目一句话：**导入试题与答案解析文本，端上解析成可随时刷题的题库。纯本地运行，不依赖云开发。**

## ADR-1 · 从云开发重构为纯本地

**状态**：已采纳（v2）｜被替代：v1 云端实现，见 ADR-6

### 约束

项目最初是云开发版：源文件传云存储，元数据与题目存云数据库（3 个集合），解析跑在云函数里（依赖 `pdf-parse` / `mammoth`）。

它的实际使用场景只有两个：
1. **自己刷题** —— 单设备、单用户
2. **作为作品集展示** —— 需要别人能快速跑起来

### 决策

去掉云存储与云数据库，数据全部落到小程序本机：
- 轻量索引进 `wx.setStorageSync`
- 题库明细与源文件进沙箱文件系统（`wx.env.USER_DATA_PATH`）
- 解析引擎搬到端上（ADR-3）

### 被否决的方案

| 方案 | 为什么否决 |
|---|---|
| 保持云开发 | 单用户场景下，云存储与云数据库没有带来任何收益，却带来一整套运维负担：开通环境、建集合、部署函数、盯配额与超时 |
| 混合（数据本地 + 云函数只做 PDF 抽取） | 见 ADR-5 |

### 后果

**收益**
- 部署从「10 分钟 + 5 个步骤」降到「填个 AppID，编译」（见 ADR-1 附带的重构后可运行性）
- 零网络依赖：除了微信自身的运行框架，应用代码不发任何网络请求
- 隐私上不劣于云版本：试卷内容不出本机
- 无云开发费用

**代价**（必须如实承认）
- **数据不跨设备、不跨微信账号**。这是去云化的核心代价，需要导出/导入 JSON 之类的功能兜底
- 用户删除小程序 / 清理微信缓存会导致数据丢失（本地用户文件的清理时机「跟代码包一样」）
- 端上解析能力有限，PDF/Word 需要电脑预处理（ADR-4）

### 重构后的可运行性（这是决策的主要动机）

| 步骤 | v1 云端版 | v2 纯本地版 |
|---|---|---|
| 1 | 替换 AppID（云开发要求非游客 AppID） | 替换 AppID |
| 2 | 开通云开发、创建环境 | — |
| 3 | 把环境 ID 填进 `config.js` | — |
| 4 | 创建 3 个数据库集合并设权限 | — |
| 5 | 部署 4 个云函数（含云端装依赖） | — |
| 6 | 把 `generateSet` 超时从默认调到 60 秒 | — |
| 7 | 编译运行 | 编译运行 |

## ADR-2 · 数据分两层存储：索引进 storage，明细进文件系统

**状态**：已采纳

### 约束

`wx.setStorageSync` 有两个硬限制：**单 key 上限 1MB、总量上限 10MB**。

而一份 1000 题的行测题库，把题干、选项、答案、解析全文序列化成 JSON 后约 **1.6MB** —— 单个 key 就超限，同步写入会**直接抛异常**。

### 决策

按「大小 + 访问频率」分两层：

| 数据 | 存放位置 | 量级 | 访问特征 |
|---|---|---|---|
| 文件清单 / 题库清单（索引） | `setStorageSync` | 几百字节 | 首页每次都要读，必须同步且快 |
| 题库明细、源文件 | `USER_DATA_PATH` 文件 | 单份 1MB+ | 打开某本书时才读，可异步 |
| 刷题进度 / 错题本 / 校对记录 | `setStorageSync` | KB 级 | 频繁读写 |

首页只读索引即可立刻渲染；打开题库时才按需读那一个 JSON 文件。

### 实测数据

5 本行测书（4909 题）共占用 **7.9MB**，平均 **1.6MB/本**。沙箱上限 200MB，可容纳约 100 本。已实测单本解析耗时 36~75ms。

### 后果

- 需要自己维护「索引 ↔ 文件」的一致性 → 由 `utils/localdb.js` 单点负责，并提供 `stats()` / `cleanOrphans()` 自查与清理孤儿文件
- 写入大 JSON 是同步操作，会有可感知停顿 → 只在生成/删除题库时发生，用 `setTimeout` 让 loading 先渲染

## ADR-3 · 解析引擎拆成「纯 JS 核心 + Node 适配层」，单向同步

**状态**：已采纳

### 约束

原来的 `parser.js` 是一个 800 行单体：顶部 `require('fs'/'os'/'path')`，`extractText` 里混着 `pdf-parse` / `mammoth`。小程序端**完全没有 Node 运行时**，没法直接用它。

同时，**小程序无法 `require` 到 `miniprogram/` 之外的目录** —— 所以核心文件必须在两端各存一份。

### 决策

```
legacy/cloudfunctions/generateSet/parser.js（原 800 行单体）
   ├─ 拆出 ─→ parser-core.js   758 行纯 JS：切题、抽答案、顺序对齐、按位置装配
   └─ 剩下 ─→ parser.js          53 行 Node 适配层：只保留 extractText
```

两份拷贝固定为「**一份真源 + 单向同步**」：
- 真源：`legacy/cloudfunctions/generateSet/parser-core.js`（直接改这里）
- 副本：`miniprogram/utils/parser-core.js`（由脚本生成，不手改）
- 工具：`node tools/sync-parser.js`（带 `--check` / `--lint` 模式）

### 怎么防止两份实现跑偏

四层防护，每层都针对一类具体失效：

| 层 | 检查 | 拦住的失效 |
|---|---|---|
| 1 | 同步脚本签名护栏：核心不得含 `require` / `Buffer` / `process` / `__dirname` | 误引入 Node 能力，真机崩溃 |
| 2 | 两份拷贝**逐字节一致** | 手改了副本、忘记同步 |
| 3 | 子进程把 `Buffer`、`process` 置为 `undefined` 后实跑一遍解析 | 「静态看着没问题、运行时才崩」的漏网情况 |
| 4 | 护栏自身的回归测试（注入违规必须拦、注释不得误报） | 护栏本身失效或误报 |

### 一个值得记录的踩坑

护栏第 1 版扫的是**原始文本**，而文件头注释里正好写着「不要引入 require / Buffer / process / __dirname」——护栏把**这句说明文字本身**判成了违规，导致同步直接失败。

修法不是改注释，而是**让护栏先剥掉注释再检查**，并补上第 4 层回归测试锁住这个行为。这类「检查工具自己先出错」的问题，如果不补测试，下次改注释还会再犯一次。

### 附带收益

核心能同时在**小程序端 / Node 脚本 / 云函数**三种环境跑，所以：
- 真实语料可以在 Node 里直接验证，不用开模拟器（见 ADR-6 的验证一节）
- `_smoke/` 全套测试无需微信开发者工具

## ADR-4 · PDF / Word 不做端上解析，改为电脑端预处理

**状态**：已采纳

### 约束

| 类型 | 端上可行性 | 原因 |
|---|---|---|
| txt / md / json / csv | ✅ | 纯文本，`readFileSync(path, 'utf8')` 即可 |
| **docx** | ❌ | ZIP 容器，需解压 + 解析 `word/document.xml`。端上没有 ZIP 库，且运行时装不了依赖 |
| **pdf** | ❌ | 需解析 PDF 对象结构、解 FlateDecode 流、再从内容流抽文字，还要处理 CJK 字体的 CID 编码映射。主流库依赖 Node 的 `Buffer` / stream |

### 决策

**分而治之**：把「字节 → 文本」这一步挪到电脑上做一次，之后全流程在本地。

```
PDF / Word  →（电脑）tools/to-txt.js → txt  →（微信发送）→ 小程序导入 → 生成题库
```

`tools/` 自带 `package.json` 声明 `pdf-parse` / `mammoth`，与小程序代码解耦（`cd tools && npm install`）。

### 端上的行为设计

- pdf/docx **允许存入文件库**（用户可能只是先留着），但打上「端上不可解析」标记
- 导入时**当场提示**并给出两条路（仍要保存 / 去电脑转换），不让用户走到「生成题库」才发现失败
- 生成向导里选到不可解析的文件会**提前拦截**并给出指引

### 后果

- 少了一个「拖 PDF 进来直接出题」的体验，多了一步电脑转换
- 换来的是：零云依赖、零运维、无需付费

## ADR-5 · 不做「云函数 + 离线」的混合方案

**状态**：已采纳（明确不做）

### 背景

很自然的一个想法：既保留离线能力，又用云函数补上 PDF/Word 解析，岂不是两全？

### 关键约束（这是决策的核心）

`wx.cloud.callFunction` 的入参**装不下几十 MB 的 PDF**（原云端实现就是这么写的：云函数只接收 `fileID`，再用 `cloud.downloadFile` 去下载）。

所以**「用云解析 PDF」必然等于「云存储 + 云函数」** —— 纯本地架构想避免的那两样东西，一个都躲不掉。

### 决策

不做。理由按重要性排序：

1. **收益接近零**。项目真实语料是行测 OCR 出来的 `.txt`（原始 PDF 是扫描版，无文字层——`pdf-parse` 对扫描版同样抽不出文字，云端也救不了）。云函数能解决的场景，被数据格式直接排除了。
2. **成本却很高**：重新引入云环境开通、环境 ID 配置、云函数部署、云存储配额、函数超时（大 PDF 要调到 60 秒）——正是 ADR-1 里花力气去掉的那一整套。
3. **破坏可运行性**。没有云环境的读者 clone 后 PDF 功能不可用，项目分叉成「有云/无云」两种用法，作品集的「一键跑起来」优势被削弱。
4. 如果真要做，唯一正确的形态是**云只做「字节→文本」这一步**，题库/进度/错题本仍全本地——但即使这样，上述 1~3 条依然成立。

### 保留的可能性

如果将来目标是「给他人做一个能直接传 PDF 的公开版」，可以按上面的正确形态实现：新增一个只返回文本的云函数、加 `cloudExtract: 'auto' | 'off'` 开关、抽完即删云端临时文件。届时应把 ADR-1 与 ADR-5 一并重估。

## ADR-6 · 云端实现归档到 `legacy/`，而不是删除

**状态**：已采纳

### 背景

`cloudfunctions/` 在小程序运行时**已完全不被调用**（`miniprogram/` 里搜 `wx.cloud` 只剩注释）。

一个自然的选择是删掉，让仓库更干净。

### 决策

整体移动到 `legacy/cloudfunctions/`，保留并在文档中说明。理由：

1. **它仍是现役依赖**。`parser-core.js` 的真源和 Node 侧的 `extractText` 适配层都在这里，`tools/sync-parser.js` 依赖它（见 ADR-3）。
2. **它是架构演进的证据**。「先交付云端版，再完成一次完整的去云化重构」——相比「一开始就写纯本地」，这段历史更能体现对两种方案的取舍判断。保留代码比只在文档里声称更有说服力。

### 收尾动作（避免它干扰项目运行）

| 动作 | 为什么 |
|---|---|
| `project.config.json` 移除 `cloudfunctionRoot` / `cloudfunctionTemplateRoot` / `cloud.envId` | 否则开发者工具导入时会提示配置云环境，让读者困惑「不是纯本地了吗」 |
| `appid` 匿名化为 `touristappid` | 避免把个人 AppID 带进公开仓库（AppID 本身不是密钥，但去云后已无用途） |
| `tools/to-txt.js` 改为依赖 `tools/` 自带依赖，`legacy/` 仅作兜底查找路径 | 消除对归档目录的隐式耦合 |
| `.gitignore` 忽略 `node_modules/`、`project.private.config.json` | 归档目录里的 149 个依赖包不入库 |

### 匿名化的副作用（踩过一次，记下来）

`touristappid` 会让开发者工具以**游客模式**打开项目 —— 启动日志里会反复提示：

```
[同步云环境列表] 需要重新登录
游客模式
请注意游客模式下，调用 wx.operateWXData 是受限的, API 的返回是工具的模拟返回
```

这些都不是故障（本项目不用云开发，日志里唯一的健康信号是 `app.js` 打出的 `[storage] 本地存储就绪`）。但游客模式有一个真实代价：**不能真机预览 / 真机调试**，手机端点不了。

| 影响 | 说明 |
|---|---|
| 模拟器开发 | 不受影响，storage 与沙箱文件系统照常工作 |
| 真机预览 / 调试 | **不可用**。真机预览要求非游客 AppID，且工具需处于登录状态 |
| 模拟器数据 | 沙箱按 appid 隔离（`User Data/<会话>/WeappSimulator/WeappFileSystem/<appid>`）。换回真实 appid 后，游客模式下导入的题库与进度不会跟着走 —— 数据仍在原目录，只是看不见 |

本地要恢复真机能力，**不要在 `project.config.json` 里改回真实 AppID**（那样一提交就又带出去了）。正确做法是写进 `project.private.config.json`：

```json
{ "appid": "你的真实 AppID" }
```

官方文档明确：`project.private.config.json` 中的相同设置**优先级高于** `project.config.json`，且「在 详情-基本信息 中修改了 appid，会写到 `project.private.config.json` 中，不会覆盖掉 `project.config.json` 的 appid 字段」。而 `project.private.config.json` 已在 `.gitignore` 里 —— 于是**仓库里永远是 `touristappid`，本地开发仍然是自己的 AppID**，两个目标同时成立。

（这也顺带照顾了克隆这个仓库的人：他们拿到的是 `touristappid`，按 README 填自己的即可。）

## ADR-7 · 用顺序对齐代替按题号匹配

**状态**：已采纳（编号按决策时间追加，本条虽为核心算法，但落地时间晚于前六条）

### 约束

真实教辅的题号会按「考点 / 小节 / 作业题」组**重新从 1 开始**。5 本真实语料实测的重置次数：**6 / 91 / 98 / 51 / 52**。

而最初的实现是按 `map[题号]` 装配答案 —— 后出现的同名题号会覆盖先出现的，**答案必然串位**。

最麻烦的是：**这个问题不会报错。** 每个题号都能查到答案，只是查到的是别人的答案。表面上「匹配率 98%」，实际答案大面积错位。

### 决策

不按题号建索引，改为「序列对齐 + 按位置装配」：

| 步骤 | 做法 |
|---|---|
| 1. 抽取答案条目 | **按文档顺序、不去重**（早期版本按题号去重，一本 988 条的解析册只剩 69 条） |
| 2. 单调 DP 对齐 | 两条题号序列做带跳过的对齐。代价：题号相同 0；两侧同时为 `1`（同节起点）0.1；差 ≤2 为 0.6；其余 2.0；单侧跳过 1.2 |
| 3. 平局取舍 | 代价相同时**优先跳过解析侧较后的条目** —— 否则多出来的一条会把后面整段答案往前拉 |
| 4. 装配 | 对齐结果**按位置**挂到题目上，不再按题号查表 |

### 被否决的方案

| 方案 | 为什么否决 |
|---|---|
| 按题号建 map | 题号重复必然串位，且串位后静默不报错 |
| 先分卷、再在卷内按题号 | 卷内同样会重置（「作业题」组会重新编号） |
| 要求答案文件的题号全局唯一 | 用户无法控制教辅的排版 |
| 严格相等，数量不等即报错（原实现） | 真实数据一定有少量缺失（OCR 漏行、多余条目），严格相等会让**整本书直接无法导入** |

### 后果

- 从「5 本里 4 本无法导入」变成「**5/5 本全部导入**」，匹配率 97.4%~98.4%
- 容忍两侧少量缺失：只把对应项留空，**不会把后面的答案整体前移**
- **滑移检测成为必要**：验证配对偏移 `j - i` 是否始终落在窄带内、有无跳变 —— 用来确认整体没有错位。这是「对齐成功」之外必须独立做的验证

### 一个反直觉的教训

**「匹配成功」不等于「答案可用」。** 匹配率统计的是「有没有找到答案条目」，而不是「答案是否非空」。所以当多选题答案被静默吞掉时（见下一节），匹配率依然显示健康的 97~98% —— 指标口径必须能区分「找到」和「可用」两件事。

## ADR-8 · 用「导出/导入 JSON」兜底数据不可迁移

**状态**：已采纳

### 约束

ADR-1 选择了纯本地，代价是**数据不跨设备、不跨账号**。删除小程序或清理微信缓存即丢失。这对「自己刷题」是必须解决的问题——用户可能刷了几个月，积累的错题本与校对记录无法用源文件重建。

### 决策

提供导出/导入，把数据打包成一个 JSON 文件，通过微信转发出去。

**包里放什么**（按不可再生程度排序）：

| 内容 | 是否必需 | 理由 |
|---|---|---|
| 错题本 | **必需** | 刷题积累的全部价值，无法重建 |
| 校对记录 | **必需** | 手工逐条核出来的勘误，无法重建 |
| 刷题进度 | 必需 | 断点续练 |
| 题库明细（题目 + 答案解析） | 必需 | 内联后导入即可直接刷题，不依赖源文件 |
| 源文件内容 | **不放** | 题库明细已自包含；一本 160KB 的 txt 转 base64 会膨胀 1/3，收益低 |

### 关键设计：幂等

导入规则是「**已存在的 setId 一律跳过**」。带来三个好处：

1. 重复导入同一份备份不会产生重复题库
2. 不会覆盖本机已有的进度（导入失败重试也安全）
3. 无需重映射 `进度/错题本/校对记录` 的存储键——它们都以 `setId` 为键，直接复用原 setId 即可

### 被否决的方案

| 方案 | 为什么否决 |
|---|---|
| 把备份内容复制到剪贴板 | 一本题库的 JSON 就 1MB+，剪贴板根本不可用 |
| 只导出题库、不含学习记录 | 正好漏掉了最不可再生的部分 |
| 导入时按标题合并 | 同名题库可能是不同版本，合并会静默产生脏数据 |
| 导入时覆盖已存在的题库 | 一次误操作就毁掉本机进度，不可接受 |
| 引入云存储同步 | 直接违背 ADR-1 与 ADR-5 |

### 发送路径的取舍

| 方式 | 覆盖 | 说明 |
|---|---|---|
| `wx.shareFileMessage`（转发到聊天） | 全平台 | **主路径**。基础库 ≥ 2.16.1；可发给「文件传输助手」保存到电脑，也可直接发给同学 |
| `wx.saveFileToDisk` | 仅 PC 微信 | 检测到该 API 存在时才在菜单里出现 |

手机端拿不到「存到电脑」的能力，所以主路径必须是「转发到微信」——这一点在实现前先查了官方文档确认，而不是先写好再发现平台不支持。

### 后果

- 换手机 / 重装：导出一次 → 新机导入，完整还原含错题本与校对记录
- 附带解决了「把题库分享给同学」：对方导入后连解析都省了
- 代价：多了一个用户需要理解的概念（备份文件），以及版本兼容的维护责任（`version` 字段 + 版本过高时明确拒绝）

## ADR-9 · 「标记」从会话状态提升为按题库持久化

### 背景

标记最初只有一个字段：刷题会话 `state.marks`。写进去很容易，但**没有任何出口**：

- 会话是按题库唯一的一份（`qz_state_{setId}`），开一次新的「顺序练习」就把 `marks` 覆盖掉
- 答题卡 `openSheet` 只生成 空白 / 对 / 错 / 已答 / 当前 五种状态，标记态不参与渲染
- 全项目没有「只刷标记题」的入口

结果是：用户标了，然后永远找不回来 —— 一个只写不读的功能。

### 约束

- 标记天然是**跨会话**的（今天标的题明天还要看），会话级存储与这个语义直接冲突
- 会话里可能已有存量标记，不能直接丢掉

### 决策

新建 `utils/marks.js`，按题库持久化到 `qz_mk_{setId}`，与错题本 / 校对本同构；会话里的 `state.marks` 退化为历史字段。

- 标记只存题号数组（题干从题库明细实时取），空清单直接删键，不占存储
- 答题卡的标记态**不参与 `cls` 竞争**，改用独立的角标元素 —— 因为 `cls` 已被「当前题」抢占，用类名叠加会让「当前且已标记」的题丢掉其中一个信息
- 新增 `mode=marked`，复用既有的 `nos` 题号直传机制，与「错题重练」走同一条路
- 进答题页时把存量 `state.marks` 并入持久化清单并清空会话里那份（幂等，重复进入不会重复搬）
- 备份要带上：标记是用户积累，不带上就等于换手机即丢

### 后果

- 标记有了完整闭环：写入 → 答题卡可见 → 首页可见「标记 N」→ 标记题重练
- 代价：多一个存储键、多一层模块。但「只写不读」的功能成本更高
- 教训：**加一个交互按钮时，要同时回答「用户之后怎么再找到它」**。这个功能卡了很久，不是因为难，而是因为没人问第二个问题

## ADR-10 · 存储写入分两条路径，把「静默」消灭掉

### 背景

`wx.setStorageSync` 在总量超过 10MB 时抛错。改造前的处理是分裂的：

| 位置 | 旧行为 | 后果 |
|---|---|---|
| `localdb.writeIdx` | 裸调 | 异常直接冒到页面，报错信息是底层 `errMsg`，用户看不懂 |
| `progress.saveState` | 裸调 | 同上，且发生在答题过程中 |
| `wrongbook.saveBook` | `catch (e) { /* ignore */ }` | **错题本无声丢失**：用户以为在积累，其实一直没写进去 |
| `errata.saveBook` | `catch (e) { /* ignore */ }` | 同上 |

最后一类最危险：它让「数据没保存」表现为「一切正常」。

### 决策

新增 `utils/safestore.js`，按调用方的诉求分两条路径：

- **`writeOrThrow`** —— 索引类是权威记录，写不进去就不能让调用方以为成功了。抛出带 `message` 的错误，交给页面现有的 `try/catch` 提示
- **`write`** —— 进度 / 错题 / 校对 / 标记是高频写，不能打断作答。失败先记进待提示现场，由页面在每次操作后 `take()` 一次并弹窗

两个细节是从测试里反推出来的：

1. **保留首次失败**。一次操作常连写多个 key（如进度 + 最近记录），后面的失败只是前一个的连带后果；若让后面的覆盖，提示文案会对应到次要的那条数据上（这条是测试先失败才发现的）
2. **页面离开时不弹窗**。`onHide` / `onUnload` 里弹窗看不见，留给下一个可见页面 `take()`，信息不丢

### 后果

- 「数据没保存」永远有一条可见的告知路径，不再有静默分支
- 容错逻辑集中在一处，新增数据层时不必各自决定怎么处理失败
- `safestore.test.js` 把「storage 写满」这个场景直接造出来验证：失败必被记录或抛出、失败时不留下半截索引、恢复写入后一切照旧
- 代价：`localdb.addFile` 这类调用现在可能抛错，调用方必须确保有 `try/catch`（页面本来就有，属于顺带收紧）

## ADR-11 · 自定义练习用「题项身份」跨题库，而不是复制题单

### 背景

需求是「先限定范围（章节 / 类别 / 知识点），再设定题量，然后随机抽题、随机顺序呈现」。

第一个要回答的问题不是 UI，而是：**范围能跨题库吗？**

查数据结构后发现「章节」在这个项目里不是题目的属性 —— `splitParts` 把章节切成**独立的题库**（一本书拆成几十个 setId，标题是「书名 · 第一章 xxx」）。也就是说：

- 「按章节筛选」= 跨多个 setId 抽题
- 若不跨库，这个功能就退化成「选择题库 + 随机」，等于首页已有的「随机练习」

所以跨库是必须的。但跨库会撞上一个贯穿全局的前提：**现有的一切（会话、错题本、标记、校对、备份）都是按单个 setId 组织的**。

### 约束

| 约束 | 说明 |
|---|---|
| 题号跨库会重复 | 每本书的题号都从 1 开始，`s1` 的第 3 题与 `s2` 的第 3 题是两道题 |
| 作答副作用必须回到原题库 | 答错要进**那一道题所属题库**的错题本，否则错题本按题库聚合的模型就废了 |
| 已存在的进度不能被迁移掉 | 历史会话的 `records` 以题号为键，动它等于丢掉用户积累 |
| 内存与渲染有硬上限 | 一本 1000 题的题库解析后 1MB+，几十个题库不能一次性驻留页面 |

### 决策

引入一层「题项身份」，把跨库这件事收敛到一个键上：

- **uid = `setId::no`**。普通会话里 uid 恰好等于题号本身，所以历史进度**零迁移**沿用；自定义练习才真正用上带 setId 的形式（`progress.itemUid` / `parseUid`）
- **答题页内部统一成题项数组** `items = [{uid, sid, no, title}]`，`goto` 只认题项；取题时普通会话查 `byNo`，自定义查预建的 `byUid`
- **副作用按题项回写**：错题本 / 标记 / 校对都用 `item.sid` 而不是页面级 `data.setId`，页面内的三本书缓存也从「单个对象」改成「按 setId 的 Map」
- **自定义会话占用固定槽位** `qz_state___custom__`：它没有唯一 setId 可挂，且「一次只进行一组」符合直觉，重新抽题即覆盖
- **题单经 storage 传递**（`qz_custom_plan`），不走 URL：抽 20~500 题的清单塞不进 query，且计划**取用即删**，避免上次的设置被静默复用
- **只加载涉及到的题库**：抽 20 题就只读这 20 题所属的库，且只把抽中的题目留在内存

### 被否决的方案

| 方案 | 否决原因 |
|---|---|
| 把抽中的题**复制**成一个临时题库（`custom_xxx`）再交给现有答题页 | 答题页不用改，但错题/标记会落到临时库上，与真实题库的错题本脱钩；临时库还会出现在首页题库列表与备份里，需要额外的过滤与清理规则 |
| 让答题页的 `setId` 随当前题动态切换 | 会话键会跟着变，等于每次翻页换一份进度 |
| 在 `records` 里把所有历史会话的题号前加前缀（统一 uid） | 需要迁移全部已有进度，收益只是让代码"看起来更整齐"，而正确性并无提升（普通会话的题号本来就不冲突） |
| 按「最近一次会话」推断「未做过」 | 那份记录只覆盖上一次练习，拿它当「做没做过」会误导用户。改用**错题本**当状态维度（曾做错过 / 已标记），语义准确 |

### 后果

- 抽题引擎（`utils/custom.js`）是纯逻辑 + 一层数据读取，可以在 Node 里完整测试；筛选、计数、抽样、随机顺序都不依赖页面
- **候选池计数是分面的**：题型选项旁边的数量已叠加状态条件、状态选项旁边的数量已叠加题型条件 —— 每个选项显示的都是「选它会有多少」，不是一个永远不变的基数
- 题量的联动只有一条路径（`recount`）：范围变 → 重算候选池 → 数量超上限就夹回并说明。界面显示的与真正抽的永远同源
- 代价：自定义练习的会话不进备份（备份结构是按 setId 的数组，为它递增版本号会让老版本拒绝导入整份备份），文档里如实写明
- 代价：删除题库后旧的自定义会话可能引用到已删的题，恢复时会剔除失效项并在全失效时明确报错，而不是让用户面对空题

## ADR-12 · 修掉「作答记录没写回会话」

### 现象

加自定义练习的测试时，断言「本次会话记录了 3 条作答」失败，`state.records` 是空的。

查下去发现这不是新功能的问题：`goto` 里写的是

```js
const rec = (s.records && s.records[item.uid]) || {};
this.curRec = rec;
```

首次做到某道题时 `records[uid]` 不存在，于是 `rec` 是一个**游离对象**；后续 `confirmAnswer` / `judgeSelf` / `tapOption` 都在改这个游离对象，改完从未写回 `s.records`。

### 影响面（比看起来大）

| 位置 | 症状 |
|---|---|
| 答题页「已答 N」 | 恒为 0 |
| 成绩页 | 已作答 / 答对 / 正确率 全为 0，交卷提示「还有 N 题未作答」永远全量 |
| 整卷回顾 | 「我的作答」永远显示「未作答」，红绿选项不着色 |
| 会话记录 | 落盘的 `records` 为空，`wrongs` 也为空 |

### 为什么一直没被发现

既有的 520 项断言里，答题页那套测的是**错题本**（走 `wrongbook` 模块，独立于会话），整卷回顾那套测的是**直接构造的 state**（自己塞好了 `records`）。**没有一条断言去检查「作答之后会话里到底有没有记录」** —— 两个模块各自都是对的，接缝处没人看。

### 决策

在 `goto` 里确保记录项存在并持有**引用**：

```js
if (!s.records) s.records = {};
if (!s.records[item.uid]) s.records[item.uid] = {};
const rec = s.records[item.uid];
```

并把「作答写回会话」补成 5 项回归断言（含落盘后再读一次），锁住这个接缝。

### 教训

**两个模块各自的测试全绿，不等于它们之间的接缝是对的。** 这次是「答题页写记录」与「成绩页/回顾页读记录」之间的缝，两边都没测自己这一端的外发/外收行为。新增功能时顺手断言一下既有链路的数据落地，比只测新写的分支更有价值。

## 附：一次「用交叉验证发现自己工具出错」的记录

这个案例值得单独写，因为它是本项目里最有价值的工程叙事。

### 现象

对 5 本书做「答案速览 vs 解析册」交叉核对，报告显示 **279 处答案不一致**，一致率只有 88%~95%。按常识，两份同一本书的答案源不该差这么多。

当时的推断是「可能是 OCR 误读，也可能存在真正的错题」，并把它列成了人工抽查清单。

### 归因过程

1. **看差异的形态**。279 处里 103 处形如 `速览/解析C` —— 左边是空的。不是「A vs B」，是「空 vs C」。
2. **查空缺为什么会出现**。追到核对脚本取字母串的代码：`l.split('|')[3]`。而速览单元文件是 **CRLF** 换行，所以取到的是 `"BCBDDBDBAA\r"` —— 末尾带了一个回车符，每个单元多出 1 个伪字符。329 个伪字符参与了对齐，其中 103 个被对齐到了具体题目上。
3. **换判据**。速览原文行其实自带**印刷题号区间**（如 `R|.+++++ 1--5 DCAAD 6--9 ACAD`），这是速览里唯一可靠的题号信息。用它做锚点分层后：**锚点吻合时两侧一致率 99.6%（2141/2149）**；锚点不吻合时才 9.6%。
4. **结论**：差异主体是「速览字母挂错题」的定位错位，**不是答案冲突**。真正锚定吻合且字母不同的只有 **8 处**，逐条读原文后：4 处确认速览侧有误，4 处无法定论。**全样本未发现任何一处解析册答案错误。**

### 结论与反思

- **上一轮「279 处不一致需人工抽查」的结论被撤回**：其中 103 处是核对脚本自己的 bug，其余大部分是定位错位。
- **解析册是权威答案源，速览不能作为逐题权威源**（它只有字母流、缺少可靠题号锚）。
- 教训：**核对工具本身也会出错，而且会以「一堆可疑数据」的形式伪装成业务问题。** 遇到「异常整齐」的异常（103 处全是同一种形态）时，先怀疑工具，再怀疑数据。

## 另一个同类发现：示例数据抓出的解析 bug

写 `samples/` 示例题库时，测试报了 4 项失败——多选和判断题的答案是空的。

追下去发现 `normAnswerKind` 只用**单字符**匹配（`/^[A-H]$/`），于是：
- 多选题 `ABD` → 判成「无答案」
- 判断题 `正确` / `错误`（两字写法）→ 判成「无答案」

更隐蔽的是：这类题**仍然显示「已匹配」**（匹配看的是有没有条目，不是答案是否非空），所以刷题时不会报错，只是答案空着。真实语料里命中 2 题，示例题库里 8 题命中 4 题。

修法：改为「先去分隔符再抽字母」，同时把 `EXPL_HEAD` 的捕获范围与归一化能力对齐（否则「捕获不到」会伪装成「没有答案」），并补 13 项回归测试锁住行为。

教训：**「匹配成功」不等于「答案可用」，指标口径要能区分这两件事。** 这个 bug 之所以长期没暴露，正是因为匹配率指标（97~98%）看起来一直很健康。

## 再一个：一次间歇性失败的测试，暴露了排序的不确定性

跑全量测试时，错题本页有个用例**偶发失败**（20 次里挂 1 次）：`分组内按错误次数排序 got=["1","3","2"]`。单独连跑 5 次又全过。

第一反应是"测试不稳定，加重试就行"。但追下去发现是**产品行为本身不确定**：

排序规则是「错误次数降序 → 最近答错时间降序」。题 2 与题 3 都只错 1 次，于是靠 `lastWrongAt` 破平局——而这两条记录是在**同一段代码里连续写入的**，落在同一毫秒还是相邻毫秒，取决于运行速度。落在同毫秒则 `Array.sort` 稳定排序保留插入顺序（题号升序），跨毫秒则"后错的排前面"。

所以这不只是测试问题：**用户反复刷同一批题时，两道"同样错 1 次"的题会莫名换位置。**

两处修：

1. **产品**：排序补上第三级兜底 —— `wrongCount` 降序 → `lastWrongAt` 降序 → **题号升序**。前两级都相同时给出确定顺序。
2. **测试**：造数据时**冻结 `Date.now`**，让用例测的是排序规则本身，而不是运行速度。修完连跑 20 次全过。

教训：**间歇性失败的测试值得追，不要靠重试掩盖 —— 它常常在提示一个真实的非确定性行为。** 这里"靠毫秒时间戳破平局"在生产环境同样成立，只是用户不容易察觉规律，只会觉得"列表顺序有点乱"。

## 选项异常：能兜底的兜底，不能兜的如实说（2026-09-23）

真数据里选项异常有四类来源，处理方式必须分开，否则会修出更隐蔽的错：

| 现象 | 根因 | 处理 |
|---|---|---|
| 同一字母出现两次（`ABCDABCD`） | 题号行漏检，两题选项粘连 | 去重，保留首次出现的那一组 |
| 序号不从 A 起 / 跳号（`BCD`、`ABD`） | 选项行被扫描漏掉 | 重排为 `ABC…`，**答案字母同步换算** |
| 选项文本挂着跨册提示、页码标记 | 页眉页脚混进正文 | 只剥尾部的固定形态噪声 |
| 答案指向不存在的选项（答案 D 但只有 ABC） | 那个选项整条丢了 | **不猜**，转自评 + 页面说明 |

关键取舍在最后一条：这类题（全库 78 处）如果保留 `answerKey`，自动判分会**永远判错**——用户选什么都错，还看不到原因。所以改成清空 `answerKey`、保留 `answer` 原文、打 `answerSuspect` 标记，让页面说清楚"选项缺失导致答案对不上"，用户仍可在「补答案」里核对。宁可少判一题，不要判错一题。

另一个容易漏的点：序号重排**必须连带换算答案**，并同步改写展示用的 `answer` 文本。只重排不换算，就会出现"参考答案 C"但 C 已经是另一条选项——比不修更糟。

数据侧效果（5035 题）：重复字母 5→0、序号跳号 75→0、不从 A 起 111→0、答案越界 78→0；转为「存疑自评」78 题。五本匹配率逐字未变，说明没有误伤任何一道本就正确的题。

## 生成页的文件槽位要有类型白名单（2026-09-23）

## 同名文件重新导入：替换会连带清题库（2026-09-23）

用户在电脑上改完 txt 想重新导入，原流程必须先去文件库删掉旧文件，否则会存成两份看不出区别的文件。改成弹冲突提示（替换 / 重命名 / 跳过）。

**冲突判据只有文件名**。沙箱里的物理路径本来就带时间戳+随机数（`localfs.uniquePath`），永远不会撞，所以重名判断只能用用户看得见的那个名字。

**替换为什么连题库一起删**：文件被同名替换，说明用户认定这份才是最新的。留着旧题库的话，「生成题库」会再多出一套同名题库，用户分不清该练哪个；更糟的是旧题仍可作答、答案却已过时。所以替换 = 覆盖文件 + `deleteSet`（含进度 / 错题本 / 校对 / 标记），二次确认弹窗里逐个列出将被删除的题库。代价是进度会丢，这个代价必须在用户点下去之前说清楚，不能替他默认。

**替换沿用原文件的 id 与分类**：id 不变，生成页已选中的引用不会失效；分类不变，同名文件的用途不会变（要改可在文件库里改）。另外先拷新文件、成功后再删旧文件——中途失败不至于两头都没了。

**重命名只动主名、保留扩展名**（`util.nextAvailableName`）。扩展名决定端上能不能解析，用户手输时如果把它改没了或改成别的，一律补回原来的。

「跳过」必须真的零改动：冲突分支在调用任何 store 写操作之前就 return。

## 组件的样式隔离：面板弹出来"看不见"（2026-09-23）

用户报「补答案按钮按不了」。查下来按钮的方法、绑定、组件注册全都正常——**面板确实弹出来了，只是页面上看不到**。

根因：`answer-sheet` 的遮罩与面板本体用的是**全局类**（`.mask` / `.sheet` / `.sheet-handle` / `.sheet-title`，定义在 `app.wxss`），而小程序自定义组件默认 `styleIsolation: isolated` 时，**app.wxss 里的类选择器对组件内部不生效**（只有标签名选择器等少数会穿透）。于是面板没有 `position: fixed`、没有背景、没有 z-index，落在文档流里被页面盖住。

同一个项目里的 `errata-sheet` 之所以正常，是因为它一开始就自包含（全用 `er-*` 私有类，wxss 第一行还写着"不依赖 app.wxss 全局类"）——**两个组件的样式策略不一致，只有依赖全局的那个坏了**。

修法两条并用：
- `answer-sheet/index.json` 声明 `"styleIsolation": "apply-shared"`，让 app.wxss 与页面样式对组件生效（该组件用了 `.btn` / `.tag` / `.row` 等十几个全局类，逐个抄成私有类不现实）；
- 组件 wxss 里**自留一份遮罩与面板的定位样式**。这四条规则是"能不能看见"的前提，重复一份换来的是：即使将来有人改了隔离级别或换了宿主页面，面板至少能弹出来、能操作。

静态检查补进 `wiring.test.js` 第 9 节：组件 wxml 用到的类如果只在 app.wxss 里存在，组件就必须声明非 isolated 的 `styleIsolation`（自带反空断言与检查器自检）。为此把判定抽成纯函数 `isolationProblems()` 便于喂样例。

## 解析册条目被 OCR 吃掉开括号（2026-09-23）

用户截图那题（01 第31题）显示"没有标准答案，暂时只能自评"，但解析册里明明有它——原文是：

```
31.答案】B。粉笔大数据：本题正确率为70.51%，易错项为C。【解析】…
```

`【` 被 OCR 吃掉了。清理链里的 `ANSW_TOK`（归一 `【答案B`/`（答案】D` 这类畸形）**要求前面有开括号**，所以这条形态漏网 → 不被识别成答案条目 → 该题在小程序里沦为无答案。全库共 26 处（01:8 / 03:1 / 05:4 / 07:8 / 09:5）。

同理还有「解析】」缺开括号的 11 处，以及反过来的「多塞一个括号」2 处（`。【（解析】`）。

修法：`build_importable.py` 新增 `fix_lost_bracket()`，三条规则各管一种畸形，**位置必须在 `reflow_paragraphs` 之后**——这两种畸形常跨行（句号在上一行行尾、"解析】"在下一行行首），段落重组把它们接到一行上才成形；放在重组之前跑，实测解析册仍有 11 处漏网（`31.答案】` 那种同行形态则不受影响）。

**验证方式（这类"补条目"的改动必须做）**：补回条目会改变该卷的条目数，理论上可能让顺序对齐整体错位一位。所以做 A/B 对比（关掉新规则生成一份旧产物，跑同一套对齐）：有答案题数 **+26 题**、**答案发生变化的题目 0 题**、内部不一致数前后完全一致（14/8/27/9/6）。结论：补回只填上了原本无答案的题，没有顶偏任何已有答案。

顺带得到一个可复用的体检指标：把"答案位"与解析文本里「故正确答案为X」的收尾定论交叉比对，全库 13875 处里 64 处不一致（0.46%），修复前后**数量完全一致**，说明是解析册正文里本来就存在的（解析正文自带别的题结论/条目粘连），属另一条线。

## 同名导入被「直接跳过」：原生弹层互斥（2026-09-23）

现象：改完题本重新导入，同名文件没有弹出「替换 / 重命名 / 跳过」，而是提示「已跳过本次导入」。

根因不是数据层（`findFileByName` / `setsByFileId` / `replaceFile` 都正确，有 64 项断言覆盖），而是**弹层结构**：

```
showModal({ confirmText:'选择处理方式', cancelText:'跳过',
  success(){ showActionSheet({ itemList:['替换原文件','重命名后导入'], … }) } })
```

1. **原生弹层互斥**：Modal 还没真正关闭时同步弹 ActionSheet，新弹层会被静默吞掉并直接走 `fail` —— 而 `fail` 里写的正是 `toast('已跳过本次导入')`。用户点了「选择处理方式」，看到的却是「已跳过」。
2. **主操作被藏进二级菜单**：这个场景下最高频的选择是「替换」，但一级按钮是「跳过」，替换要再点一层才够得着。

修法：把顺序反过来、并减少一层。

- 冲突第一层改用 **ActionSheet 三选一**（`替换原文件（清除 N 个题库）` / `重命名后导入（保留两份）` / `取消本次导入`），替换第一眼可见；后果的详细清单留给替换前的二次确认 Modal。
- 重命名确定后**沿用原文件分类直接保存**，不再弹角色选择（同名的文件用途不会变），顺带消掉这一处嵌套。
- 普通保存流程里「不可解析类型」的风险提示**挪到选完分类之后**，保持 ActionSheet → Modal 的方向。

约定：**只允许 ActionSheet → Modal，不允许 Modal → ActionSheet。** `wiring.test.js` 第 10 节加了静态检查（括号配对取 `wx.showModal({…})` 的参数块，块内出现 `wx.showActionSheet` 即报错；剔行注释，带反空断言与四项检查器自检）。

## 三处纠错流程行为调整（2026-09-24）

### 1. 已有未完成进度时，主按钮是「继续」而不是「重新开始」

`pages/quiz/quiz.js`。原来主按钮叫「重新开始」，success 里直接 `build()` 新建会话 —— 一点就覆盖整套未完成进度，且不可恢复。而「点进练习页」的真实意图多半是把没做完的做完，所以主按钮改为「继续」，走恢复旧会话那条路。

为此把「恢复会话」从 `mode === 'continue'` 分支抽成 `resume()` 供两处共用：兼容题库变更（剔除已不存在的题目）、夹紧位置，并同步 `mode` / `modeTag` / 导航栏标题 —— 上次做的是随机、这次点顺序时，标签要跟着会话走，不能指错。

**能力取舍**：这样就没有「重新开始」的入口了（要重做只能换模式或删掉会话）。如果后面觉得需要，再在练习页里给它一个不显眼的位置，而不是放在「点进来第一眼就点」的主按钮上。

### 2. 补答案后归入「校对清单 → 已修」

判定依据是「本机改得动什么」，定义在 `utils/errata.js` 的 `LOCAL_FIXABLE = { answer: 1, explanation: 1 }`，补答案面板与纠错面板共用这一份：

- 该题记录的问题类型**全部**落在答案/解析上 → 这次补答案就是把它修完了 → `status = 'fixed'`；
- 还牵扯题干/选项/缺图/重复错位 → 本机永远改不动，继续留「待修」，等回源文件处理；
- 解决不了的不动状态 —— 用户手动标过「已修」的，不会因为又补了一次答案被退回待修。

同时修掉一个信息丢失：`answers.saveAnswer` 原来把 `types` 交给 `upsert` 覆盖，用户在答题页勾的「题干有误」会被一次补答案抹成「答案有误」。现在**已有类型优先保留**，只有首次记录（原先没有类型）才用本次实际改动的字段当类型。

反向也补齐了：纠错面板保存时，若勾了本机改不了的类型，状态显式退回 `open` —— 否则一条已修的题再报新问题，会永远停在「已修」里看不到。

### 3. 补答案后先展示「改成了什么」，再关面板

`components/answer-sheet`。原来保存成功只弹一个 toast 就关闭，用户没法确认到底改成了什么样。现在 `save()` 不直接关，而是切到「修改结果」视图：

- 题干、选项按**最终值**渲染（选项标出正确项）—— 这两项本机不改，就如实呈现最终态；
- 答案、解析给**前后对比**（`saveAnswer` 本来就返回 `before` / `after`），没改动的字段只显示最终值并标「（未改动）」；
- 点「完成」才 `triggerEvent('close')`。

对应地 `pages/quiz` 的 `onAnswerSaved` 不再自己关面板（否则结果视图一闪就没），并顺带刷新校对记录标记。清空结果视图放在 `reset()` 里，重开面板即回到编辑态。清单页原本就有「原 → 改」对比，两者口径一致。

## 面板里的长文本盖住底部按钮：textarea 是原生组件（2026-09-24）

现象：校对面板里要改的内容一多，解析框里的文字直接压过底部的「保存」。

根因不是布局写错，而是 **`textarea` 是小程序的原生组件**：层级最高（`z-index` 无效），
而且**不会被 `scroll-view` 裁剪**。`.er-body` 是 `flex:1; min-height:0` 的滚动区，
盒子高度本身是对的；但 `auto-height` 的 textarea 会按内容长到上千 rpx，**画在盒子外面**，
于是盖住了同在 `.er-sheet` 里的 `.er-foot`。

- 滚到哪儿都躲不掉：只要内容溢出，滚动区上下两侧的 textarea 都会画到盒子外（往上盖标题、往下盖按钮）。
- **微信开发者工具里看不出来**，只有真机复现 —— 不能靠肉眼在模拟器里验收。

修法（errata-sheet 与 answer-sheet 一起改）：

1. **同一时刻只放一个 textarea。** 字段默认是只读的普通 `view`（`max-height` 折行裁掉，
   普通组件会被正常裁剪），点一下才换成输入框。静止状态下 DOM 里没有原生组件，
   滚到哪儿都盖不住别人；编辑时键盘占着下半屏，刚点的那一行用 `scroll-into-view` 顶到可视区。
2. **高度写死**：去掉 `auto-height`，内容超出由 textarea 自己内部滚动。

`wiring.test.js` 第 11 节加静态检查：组件 wxml 里的 `textarea` 不得出现 `auto-height`
（带反空断言与三项检查器自检）。这条只能静态守 —— 运行时断言测不出来。

## 「已修 / 待修」的判定：以「有没有写下修正内容」为准（2026-09-24）

上一轮把「补答案算不算修完」定为「问题类型是否全落在 `LOCAL_FIXABLE`（答案/解析）」，
并在校对面板里反向套用了同一条：勾了本机改不了的类型（题干/选项/缺图）→ 退回「待修」。

结果用户在校对面板里**把正确内容都写下来了**，记录还是挂在待修名单里。

纠正后的规则 —— 两个入口各按自己的语义判：

| 入口 | 判据 | 理由 |
|---|---|---|
| 答题页补答案 | 记录的问题**全部**落在答案/解析上 | 补答案只动得了这两项，题干本身的问题它解决不了 |
| 校对面板 | 写下了与原文不同的修正内容（`hasChange`） | 本机没有别的地方可改，把内容写清楚这件事本身就算做完了 |

并且面板的保存**只升不降**：没写内容就传 `status: undefined`、原状态原样保留，
要退回待修用清单页的开关。之前「随手保存一次就把已修冲回待修」正是这一轮报的毛病。

新增 `errata.originalOf(setId, question)`：给出这条记录当前的「原值」快照
（没有记录就用题目本身的值，取法与 `upsert` 首次写入完全一致，否则比对会失真），
供 `hasChange` 判定使用。

## textarea 绝不能待在 scroll-view 里（2026-09-24）

上一轮我把「长文本压住保存按钮」归因为 `auto-height`，改成「同一时刻只放一个写死高度的 textarea」——
用户真机复测：「依然被压住」。查下来**上一轮只解决了一半**。

真规则是：**textarea 是原生组件，画在独立的原生层上，原生层不受 scroll-view 裁剪。**
于是只要它待在滚动内容里：

- 内容一长 → 它按内容长高、画到滚动区外面（这是上一轮修的）；
- **写死高度也挡不住** —— 滚动位置让它的盒子越出可视区时，WebView 会把越出的部分裁掉
  （那块地方变空），但原生层照旧整块画在原来的页面坐标上，盖住滚动区下面的底部按钮。

所以「高度写死」只是半个规则，`wiring.test.js` 第 11 节的检查也是半个。补上另一半（第 12 节）：
**组件 wxml 里的 textarea 一律不得出现在 `scroll-view` 内部**（标签栈扫描，剔注释，
带反空断言与四项检查器自检）。

结构上的解法（errata-sheet 与 answer-sheet 一起改）：

| 状态 | 正文区放什么 | 输入框 |
|---|---|---|
| 列表态 | `scroll-view`：问题类型 + 各字段**只读**展示 | **没有**（正文里一个 textarea 都没有） |
| 编辑态 | 只放那一个输入框，面板高度写死（86vh / 80vh） | 唯一一个，高度 = 正文区高度 |

只读展示则交给「按内容定高的框」：`util.boxOf(text, maxLines)` 按折行行数算高度、
封顶 maxLines 行，超出时把 `view` 换成 `scroll-view` 在框内滚（用户要的「滚轮」）。
高度按内容算而不是写死，是因为「答案」常常就一行，固定给 6 行高会留一大片空白。

## 已有未完成进度：三条路，改用选项表（2026-09-24）

系统弹窗只有「确认 / 取消」两个钮，塞不下三条路。所以 `wx.showActionSheet` 三选一：

继续（第 2 题 · 已答 0/3）          ← 不动记录，接着做
从第 3 题开始（清空记录，从这道题重做）
重新开始（清空记录，从第 1 题重做）

- 「当前题目」= **这次点进来的那道题**（预览页 / 答题卡跳题带过来的 `start`），

## 校对面板的改动写回题库明细（2026-09-24）

现象：在校对面板里把题干/选项/答案/解析都改对了，练习页还是旧内容 ——
因为面板只写「校对清单」，那份是给回源文件改用的对照，题库明细根本没动。

改法：`utils/answers.js` 把原来只改答案/解析的 `saveAnswer` 拆成两层。

- **`applyFix(setId, no, patch)`** —— 通用的一层：题干、选项、答案、解析都能写回，
  并同步错题本快照（题干/选项/答案/解析/题型）、重算 `matchedCount`。
  - 选项从文本框回来（`errata.optionsToText` 的格式）→ `optionsFromText` 还原成数组：
    首行带字母就按字母解析（不带字母的行算上一项换行续写），整段都没字母就一行一个、按顺序补 A/B/C…
  - 答案是选项字母 → 归一后同时写 `answerKey` 与 `answer`（判断题的「正确/错误」也走这里）；
    写成一句说明 → 只当参考答案，不动答案键；清空 → 答案键一起撤掉。
  - **空补丁直接返回、不写盘**（`changed: false`），免得「只是打开看了一眼」也变成一次写入。
- **`saveAnswer(setId, no, patch)`** —— 补答案面板：`applyFix` + 记一条校对记录，语义不变。

面板侧只把**确实改动了的字段**写回（`patchOf`：draft 与题库现值逐项比对），
不写回没动过的项 —— 避免「打开面板」把题干/选项顺手重写一遍。

写失败（题库被删 / 重新导入过）时：**清单照记**（用户写的东西不能丢），但弹窗明确说明
「已记入校对清单，但没能写回题库」—— 不能让他以为改好了。

写回后 `pages/quiz` 的 `onErrataSaved` 把新题目换进内存并重渲染当前题（`applyFreshQuestion`，
与补答案那条路共用），否则题卡上仍是旧内容。

**没做的一件事**：不重判已经作答的记录。答案键变了、旧判定可能不再成立，但重判要连带
调整错题本统计（可能重复计数），风险大于收益；已知取舍，写在这里备查。

## 面板底部按钮区：正文区高度算死 + 按钮条实心置顶（2026-09-24，第三轮）

「内容压住保存按钮」真机上报了**两轮**（09-23 补答案面板、09-24 校对面板的备注区）。
前两轮的修法（只读框封顶 + 编辑态只留一个 textarea + 禁 `auto-height` + 禁 textarea 进 scroll-view）
方向对，但仍不够：**只要正文区的高度是"撑出来的"，就还有漏的可能**。

这次换思路 —— 不追"让内容别越界"，而是**让越界也影响不到按钮**：

1. **正文区高度算死**（`errata-sheet`）：`bodyHeightOf()` 纯函数算，结果写进 `style`（px）+ `flex:none`
   - 列表态 = `min(内容自然高, 可用高)`；编辑态 = 可用高（输入框撑满）
   - 可用高 = 面板上限 `86vh` − 面板里正文以外的高度（192rpx 固定 + 标题/副标题**实测**高度 + 底部安全区）
   - 「内容自然高」用 `.er-inner` 这层量（不受正文区高度影响）；标题/副标题用 `createSelectorQuery` 实测，
     不写死 —— 系统字号会被用户放大
   - 不靠 flex 把 scroll-view 压回剩余空间，也不指望滚动容器裁剪 —— 这两件事真机上都不牢靠
2. **底部按钮条成为「实心条」**：`background: #fff` + `position: relative` + `z-index: 2`
   —— 漏出来的内容只会被它盖住，按钮永远点得到
3. **面板容器 `overflow: hidden`**：自己兜住任何越界内容（两个面板都加）
4. 静态守住：`wiring.test.js` 第 13 节检查上述三条 + `bodyH` 绑定 + `er-inner` 量尺存在

## 写回题库：落盘后回读校验 + 只回传「盘上那份」（2026-09-24）

用户报「改了选项，刷题还是旧版本」。离线把整条链路跑一遍（改选项 → 保存 → 题卡刷新 → 重进）
是通的，所以问题不在逻辑本身，而在「真机上到底写进去了没有」和「页面拿的是哪一份」。两点加固：

- **`applyFix` 落盘后回读校验**（返回 `persisted`）：写完重新 `loadSetBundle` 取该题，
  逐项比对 patch 涉及的字段。不一致 → 面板弹窗明说「已记入校对清单，但没能写回题库」。
  题库明细是沙箱里的大文件，写入被截断/写到别处都出现过 —— 当场发现比等用户刷题时好。
  返回值同时给 **`latest`**（盘上那份题目），面板与练习页都用它，不用内存里刚拼的那份。
- **没写回时不回传题目**：原来保存一律把 `question` 回传给练习页，而 `applied === 0` 时
  那份是「面板带进来的旧快照」→ 会把练习页内存刷成**更旧**的版本。现在没写回就传 `null`。
- **保存文案分三种**：`已写回题库 · 已修` / `已写回题库` / `已记入校对清单，题库无改动`。
  原来「只勾类型、没写内容」也报「已保存」，用户会以为题目改好了 —— 正是这个误解的来源。
- **回到练习页时重读题库**（`quiz.onShow` → `syncFromStore`）：题目可能在别处被改过
  （校对清单页补答案、别的入口写回），内存里那份是旧的就会一直显示旧内容。
  只做单题库会话；自定义练习跨库、由抽题计划决定，不重读。题库被换过（当前题号不存在）时保持原样，不清空页面。

### 面板预填以题库现值为准（2026-09-24）

原来预填优先用「历史修正值」（`f.stem / f.options / …`），理由是"我写过的东西不能丢"。
但这会制造一个假象：**写回失败时，面板里显示的是我写下的修正，看起来像已经改好了**，
一刷题还是旧的 —— 用户那句「我明明改过了」就是这么来的。

改成：**题库现值优先**（`q.stem` / `errata.optionsToText(q.options)` / `q.answerKey || q.answer` /
`q.explanation`），题库里本身为空才退回历史记录（不丢用户的输入）。
两者不一致时，在正文区顶部挂一条 `er-stale` 提示：「上次记下的修正还没进题库：答案＝D」——
把"没生效"摆到台面上，而不是让人自己发现。
（提示放在正文区里而不是面板顶部：正文区高度是算死的，多一块固定高度的东西会撑破布局。）

**排查指引（给后来人）**：再收到「改了没生效」先看两件事 ——
① 保存时 toast 是哪一句（第三句说明面板内容与题库一致，根本没写回）；
② 关掉面板题卡有没有立刻变（变了 = 内存已同步；没变 = 写回失败，或跑的是旧包）。

## 自带一套无版权合成语料（2026-09-25）

**问题**：端到端验证依赖 5 本行测 OCR 文本，那些教辅**有版权，不能进仓库**。
结果是 `realdata.test.js` 在没有语料的机器上直接跳过 —— 别人 clone 下来跑不了，
README 里那张「4909 题、97.4%~98.4%」没有任何人能复现，等于只有自己能验证。

**决策**：自造一套语料（`fixtures/`，由 `tools/gen-fixture.js` 生成），而不是去找现成数据集。

为什么不找现成的：中文题库数据集的许可几乎都是 unknown 或 CC BY-NC，没有干净的；
就算找到，格式也对不上引擎要处理的那些边界，测了个寂寞。
自造的许可依据（都写进了 `fixtures/README.md`）：

- 数学题程序生成、答案由计算得出 —— 不存在"复制"；
- 古诗填空取唐宋名句 —— 作者逝世远超 50 年，属**公有领域**；
- 常识题写的是客观事实 —— **事实本身不受著作权保护**，表述由脚本自行组织；
- 干扰项按数值邻近/同类混淆自动生成。

**收益不只是"能跑"**：语料里刻意插了真实 OCR 语料里会搞乱切题的每一种形态
（表格数值行、水印行、方法讲解块、材料块、题干续行、题号+年份，且用 CRLF），
所以它同时是一份回归夹具 —— 改了解析规则，跑一遍就知道有没有打坏边界。
三条链路各一份语料：顺序对齐（分卷）/ 按题号对齐（单卷 + 聚合、单行多题）/ 文末自带答案。

## 解析引擎的两条已知边界（2026-09-25，造语料时实测出来的）

这两条不是 bug，是为「防止表格碎片变成伪题」付的代价，写下来免得后来人重复踩。

**① 方法讲解块 / 材料块之后的无选项题会被一并跳过。**
`splitQuestions` 在 `inMethod` / `inMaterial` 状态下，编号行必须通过
`looksLikeRealQuestion`（带题源标注，或**随后 14 行内读得到选项行**）才被认作题目。
判断题、简答题没有选项行 → 直接被跳过（实测：块后紧跟一道判断题，那题就消失了）。
造语料时把噪声块放在「后面跟有选项的题」之前，就是为了避开这条。

**② 顺序对齐路径下，判卷题答案写成纯 `1. 对` 捕获不到。**
`EXPL_HEAD_PLAIN` 要求答案位以 `[A-Ha-h]` 开头（注释解释了原因：否则「正确」会被逐字吃掉只剩「正」），
所以只有带「答案」关键字的写法（`1. 答案：对` / `1.【答案】对。`）才进得了顺序对齐。
真实解析册里判卷题都带这个前缀，所以没出问题；但要造测试数据就得照这个规矩来。

**顺带确认**：聚合式（`1-5. A B C D A`）与单行多题（`1.A 2.B`）只在**题号全局唯一**的
按题号对齐路径下生效；顺序对齐走的是 `parseAnswerEntries`，不认这两种写法。

## 答案与题目形态自相矛盾时，放弃这条答案（2026-09-26）

**现象**：用户报「判断题和单选题的判断出了问题」。截图里一道四选一的古诗填空题
（`「白日依山尽」的下一句是：` A~D）被标成「判断题」，选项照旧展示四条。

**根因**：`buildOne` 原先无条件信任答案条目的形态 —— 只要答案文件里那条写的是
`对 / 错`，就 `type = 'judge'`、`answerKey = 'A' 或 'B'`。题目自己有没有选项、有几个，
完全不看。于是出现一道**带 4 个选项的判断题**：界面展示 A~D，判分却把 A 当「正确」、
B 当「错误」，考生选 C、D **永远判错** —— 而且从界面上完全看不出哪里不对。

**成因场景**：答案解析文件选错了（顺序对齐仍会硬配 N 条），或答案在配题时串了位。
用户这一步就是「单卷题本 + 另一本书的分章解析」。

**决策**：`entry.kind === 'judge'` 时先看题目自己的形态，**只认 0 或 2 个选项**：

| 题目选项数 | 判定 | 理由 |
|---|---|---|
| 0 | 判断题，补 `A 正确 / B 错误` | 题本常态，判断题本来就不印选项 |
| 2 | 判断题，沿用题本自己的选项 | 题本把「A.正确 B.错误」印出来了，照样成立 |
| 1 | 放弃，转自评 | 另一条多半是 OCR 丢的；留着「错」这个答案无处可选 |
| ≥3 | 放弃，转自评 | 判断题只有两种状态，与三选一以上不可能同时成立 |

「放弃」= 清空 `answerKey`、保留 `answer` 原文（页面上仍能看到「标准答案写的是『正确』」）、
打 `answerSuspectKind = 'typeConflict'`，由页面说明原因并引导去核对答案文件。
这条与既有的 `missingOption`（答案指向的选项整条丢了）共用 `answerSuspect` 这一布尔标记，
但**原因分开记**：两者的处置建议完全不同（一个去补选项，一个去查答案文件配错）。

**连带修掉的两处**：

1. `answers.applyFix` 原先不清 `answerSuspect`。用户人工补完答案后，题目卡上仍挂着
   「标准答案对不上选项，请核对」—— 他已经核对完了。现在凡动过答案/选项就按结果重算：
   判分键落在选项内 → 撤掉标记；落在选项外 → 记为 `missingOption`。
2. 题本自带的**文末「参考答案」区**原先只在「没配答案文件」时切掉。另配了解析文件时，
   整段答案速览会被当成题目 —— 一本 20 题的卷子冒出 20 道假题，还把真题的答案挤到假题身上。
   现在无论答案来自哪里都先切。

**没做的事**：不去猜「字母答案 + 无选项」是不是判断题。那需要假设「A = 对、B = 错」，
而不同教辅的约定并不统一，猜错就是新的判错源 —— 沿用现状（转主观题、展示参考答案、不自动判分）。

**护栏**（都是先跑旧写法确认能抓到回归，再留下的）：
- `parser.test.js`：0/1/2/≥3 四种选项数各一条，外加「判分键必须落在选项内」这条不变量。
- `fixture.test.js`：真造一次错配（单卷 + 分章解析），断言矛盾答案一律不带判分键；
  并对全部四套题库跑一遍全库不变量（含「不允许存在 3 个以上选项的判断题」）。
- `wiring.test.js` 第 14 节：引擎产出的每种 `answerSuspectKind`，答题页都必须有对应说明 ——
  新增一类原因却忘了写分支的话，那道题会既不判分、又不解释，只有真机点到才看得出来。
- `wiring.test.js` 附带的另一条：`answerSuspect` 一律由 `answerSuspectKind` 推导，
  不许在别处单独赋 `true`（两处各写各的迟早会不一致）。

## 首页题库操作弹层：让面板自己承接滚动（删除/取消不做固定底栏）

### 现象（真机截图）

点开某个题库的操作弹层（顺序练习 / 随机练习 / 错题重练 / 导出 / 删除…），
在选项多的题库上：

1. **「删除该题库」被切在屏幕外** —— 面板一直往下堆，底部两条按钮看不见；
2. **滚轮滚不动弹层，反而把后面的首页题库列表滚了**。

### 根因

弹层是 （），只给了  和 ，
**既没有 ，内部也没有滚动容器**。这是同一类问题的第三次出现：

-  只限制「盒子能长多大」，**不限制内容画到哪**
- 内容比盒子高 → 溢出的部分照画，超出  的部分落到屏幕外（= 按钮点不到）
- 更关键：**弹层自身没有任何可滚动区域**，滚轮事件就没有「被吃掉」的地方，
  于是按事件冒泡继续传给下面那层正在滚动的首页列表 ——
  用户看到的现象是「我在滚弹层，动的却是题库列表」

### 第一版处置（错的，已回退）

拆成三段式：头部固定 + 正文  + **删除/取消固定底栏**。
理由是「破坏性操作永远可见」。**真机上立刻暴露新问题**：固定底栏会
**盖住正文里还没滚到的内容** —— 「导出该题库（含错题本与校对记录）」被压在
底栏下面，比原来更遮挡。可见的代价换来了不可见的代价，不划算。

### 最终处置



三处要点：

1. **整条一起滚。** 删除和取消放在滚动区内部，跟其他项一样滚到底才出现 ——
   既不遮挡内容，也仍然可达。**不要再做固定底栏。**
2. ** 必须有。** flex 子项默认 ，不写这条它不会收缩到
   容器之下，滚动区高度会被内容顶开 —— 溢出照旧。这是 flex 布局里最反直觉的一条。
3. **面板本体  设成禁止**，滚动只交给 ，避免双重滚动
   （外层先滚到底、内层才开始滚，手感很怪）。

顺带补上  —— 原先面板内点击会冒泡到遮罩，滚动区里点一下就误关弹层。

### 为什么做成静态护栏

数据层、组件 JS、页面 JS 全是对的，**没有任何断言能发现它**，只有真机点开才看得见。

其中「删除/取消在滚动区内」这条是**从第一版的错误里学来的** ——

### 教训

「把重要按钮抽出来固定住」听起来永远是对的，但在**小屏 + 长列表**的组合里，
固定底栏的代价是遮住内容本身。这里三次改动的方向各不相同：
第一次解决了「按钮点不到」，第二次解决了「内容被挡住」，
第三次才发现「滚动根本没生效」——
**结构对了不等于行为对了；凡是滚动容器，先确认它有没有一个确定的、小于内容的高。**
