# 去云化 + 本地文件改造：方案与评估

> 目标：让刷题小程序**不再依赖云存储**，数据保存与处理全部走本地；并尽可能放宽文件载入的来源限制。
> 本文回答四件事：**调整了哪些模块、涉及哪些权限与接口、实现思路、以及会遇到什么限制**。
> 文中所有平台结论均以微信官方文档为准，关键处附原文依据。

---

## 0. 结论速览

| 诉求 | 能否做到 | 结论 |
|---|---|---|
| 数据不再依赖云存储 | ✅ **已完成** | 数据 100% 落在本机：轻量索引进 `wx.setStorageSync`，题库明细进沙箱文件系统。已用真实语料验证 |
| 文件解析不再依赖云函数 | ⚠️ **部分完成** | 纯文本（txt/md/json/csv）端上直接解析；**PDF / docx 端上做不到**，改为电脑端预处理（已提供工具） |
| 从设备任意位置选择文件 | ❌ **小程序平台做不到** | `wx.chooseMessageFile` 的官方定义就是「**从客户端会话选择文件**」，小程序没有通用文件选择器。需要换运行时（见 §4.4） |

一句话：**存储的本地化是彻底的；文件来源的"任意位置"是平台硬限制，只能靠换运行时或加一步中转来解决。**

## 2. 目标架构

```
┌─────────────────────── 小程序端（全部本地） ───────────────────────┐
│                                                                    │
│  页面层   index / files / generate / preview / quiz / result       │
│           wrong / errata                                           │
│              │  只依赖统一门面，不再出现 wx.cloud.*                  │
│              ▼                                                     │
│  门面层   utils/store.js        文件导入 · 题库生成 · 读取 · 删除    │
│              │                                                     │
│      ┌───────┼────────────┬──────────────┐                        │
│      ▼       ▼            ▼              ▼                        │
│  localfs  localdb    extract-local  parser-core                   │
│  沙箱文件  本地数据层   端上文本抽取   解析引擎（纯 JS）             │
│      │       │                          ▲                         │
│      │       │                          │ 同一份代码               │
└──────┼───────┼──────────────────────────┼─────────────────────────┘
       │       │                          │
       ▼       ▼                          │
  USER_DATA_PATH  +  setStorageSync       │
  （200MB，读写自由）  （10MB，索引）        │
                                          │
┌─────────────────── 电脑端（可选预处理） ─┼─────────────────────────┐
│  tools/to-txt.js     PDF / docx → txt ──┘                          │
│  tools/sync-parser.js  同步解析引擎（防止两端漂移）                  │
└────────────────────────────────────────────────────────────────────┘
```

### 存储分工（这是本方案的第一个关键设计）

| 数据 | 存放位置 | 为什么 |
|---|---|---|
| 源文件（导入的 txt 等） | 沙箱 `q_source/` | 单文件可能几 MB，storage 装不下 |
| 题库明细（题目+答案解析） | 沙箱 `q_sets/{setId}.json` | 单本约 1000 题，含解析 1MB+，**storage 单 key 上限 1MB 会直接失败** |
| 文件清单 / 题库清单（索引） | `wx.setStorageSync` | 只有几百字节；同步读取，首页能立刻渲染 |
| 刷题进度 / 错题本 / 校对记录 | `wx.setStorageSync`（原有） | 本来就本地，量小 |

> 实测：5 本行测书共 4909 题、7.9MB —— **平均一本约 1.6MB**。沙箱上限 200MB，够放约 100 本。

### 3.3 云端实现已归档到 `legacy/`

原 `cloudfunctions/` 整体移到了 `legacy/cloudfunctions/`，作为 **v1 云端实现的历史存档**：

- **不再被任何运行路径调用**。`miniprogram/` 里搜 `wx.cloud` 只剩注释，代码中一句都没有。
- **不干扰运行**。`project.config.json` 已去掉 `cloudfunctionRoot`，开发者工具导入时不会再提示配置云环境。
- **保留它的两个理由**：一是解析引擎的真源（`parser-core.js`）与 Node 侧 `extractText` 适配层仍在这里，`tools/sync-parser.js` 依赖它；二是它记录着「先做云版、再做完整去云化重构」这段架构演进。

`tools/to-txt.js` 已改为**依赖 `tools/` 自带的 `package.json`**（`cd tools && npm install`），只把 `legacy/` 当作找不到依赖时的兜底查找路径，不再隐式耦合。

## 4. 权限与接口

### 4.1 本方案实际用到的接口

| 接口 | 用途 | 是否需要申请权限 |
|---|---|---|
| `wx.getFileSystemManager()` | 拿到文件系统管理器 | 否 |
| `wx.env.USER_DATA_PATH` | 用户文件根目录 | 否 |
| `FileSystemManager.mkdirSync / readFileSync / writeFileSync / copyFileSync / unlinkSync / rmdirSync / statSync / readdirSync / accessSync` | 目录与文件读写 | 否 |
| `wx.setStorageSync / getStorageSync / removeStorageSync / getStorageInfoSync` | 索引与进度存储 | 否 |
| `wx.chooseMessageFile` | 选择要导入的文件 | 否 |
| `wx.showToast / showLoading / showModal / showActionSheet / setClipboardData` | 交互 | 否 |

**结论：不需要任何额外权限申请、不需要用户授权弹窗、不需要后端域名配置。** 这套接口全部是小程序基础能力，`wx.chooseMessageFile` 需基础库 ≥ 2.5.0，本地用户文件需 ≥ 1.7.0。

### 4.2 官方能力边界（原文依据）

**文件系统容量与权限**（[官方文档 · 文件系统](https://developers.weixin.qq.com/miniprogram/dev/framework/ability/file-system.html)）：

> - 本地临时文件：运行时最多存储 4GB……小程序退出后……超过 2GB 会清理至少于 2GB。
> - 本地缓存文件：……跟本地用户文件共计，小程序（含小游戏）最多可存储 200MB。
> - 本地用户文件：……允许自定义目录和文件名。跟本地缓存文件共计，小程序（含小游戏）最多可存储 200MB。

读写权限表（原文）：

| 接口、组件 | 读 | 写 |
|---|---|---|
| 代码包文件 | 有 | **无** |
| 本地临时文件 | 有 | **无** |
| 本地缓存文件 | 有 | **无** |
| **本地用户文件** | **有** | **有** |

> 这就是本方案选 `USER_DATA_PATH`（本地用户文件）而不是 `wx.saveFile`（本地缓存文件）的原因：**只有本地用户文件可写、可自定义目录文件名**，且上限与之共享 200MB。

**本地缓存容量**：官方文档为 **10MB**（本方案只把几百字节的索引放这里，不会逼近上限）。

### 4.3 为什么"任意位置选文件"做不到

`wx.chooseMessageFile` 的官方功能描述只有一句：

> **功能描述：从客户端会话选择文件。**
> 参数：`count`（必填）、`type`（`all`/`video`/`image`/`file`）、`extension`（仅 `type==file` 时有效）
> 返回：`tempFiles[]` → `path`（**本地临时文件路径**）、`size`、`name`、`type`、`time`

配套事实：

1. 小程序**没有** `wx.chooseFile` / `wx.chooseDiskFile` 之类的通用文件选择器 API。可选文件的接口只有三族：`chooseMessageFile`（会话文件）、`chooseMedia` / `chooseImage` / `chooseVideo`（图片视频）、`chooseLocation`（位置）。
2. 沙箱是**按用户 + appId 隔离**的："同一台手机，每个微信用户不能访问到其他登录用户的文件，同一个用户不同 appId 之间的文件也不能互相访问"。小程序**无法**读取设备上任意路径。
3. `wx.getFileSystemManager()` 只能操作沙箱内的 `USER_DATA_PATH`，不是宿主文件系统。
4. `wx.saveFileToDisk`（仅 PC 微信）方向相反——只能把沙箱内文件**另存出去**给用户，不能反向读取。

所以在微信小程序这个运行时里，**"从设备任意位置选择并载入文件"是没有 API 支撑的**，不是绕一下就能实现的问题。

### 4.4 三条替代路径

| 方案 | 任意位置选文件 | 改造量 | 说明 |
|---|---|---|---|
| **A. 维持小程序 + 一步中转**（当前已实现） | ⚠️ 间接 | 已完成 | 文件先发给「文件传输助手」→ 小程序从会话导入。**电脑版微信**的选择器用系统文件对话框，可以从本机目录里挑文件，比手机端方便得多 |
| **B. 做一份 H5 版** | ✅ | 中 | 浏览器 `<input type="file">` 直接打开系统文件对话框；进阶用 **File System Access API**（`showOpenFilePicker` / `showSaveFilePicker`）还能**回写原文件**，对"边刷边改源文件"最贴合 |
| **C. 打包成桌面 / App**（Electron、Tauri、uni-app） | ✅ | 大 | 完全文件系统访问；`uni-app` 可一套代码同时产出小程序 + App，App 端用 `plus.io` 访问任意路径 |

方案 B 的可行性值得强调：**解析引擎已经是零依赖纯 JS**，`store.js` 的数据层只要把 `wx.getFileSystemManager` + `wx.setStorageSync` 换成 IndexedDB / localStorage，页面逻辑几乎可以原样搬过去。如果"任意位置选文件 + 直接改源文件"是刚需，B 是性价比最高的一步。

## 5. 实现思路

### 5.1 为什么题库明细必须落文件，而不是 storage

这是改造中最容易踩的坑。`wx.setStorageSync` 有两个限制：单 key 1MB、总量 10MB。而一本 1000 题的行测书，把题干、选项、答案解析和解析全文序列化成 JSON 后约 **1.6MB** —— 单 key 就直接超限，同步写入会抛异常。

所以拆成两层：**索引进 storage（小、要快），明细进文件系统（大、可慢）**。首页只读索引，能立刻渲染；打开某本书时才按需读那一个 JSON 文件。

### 5.2 解析引擎：一份代码，两端跑

原来 `parser.js` 800 行是一体的，顶部 `require('fs'/'os'/'path')`，中间混着 `pdf-parse` / `mammoth`。小程序端没法用它。

拆分方式：

```
parser.js（原 800 行）
   ├─ 拆出 ─→ parser-core.js   758 行纯 JS：切题、抽答案、顺序对齐、按位置装配
   └─ 剩下 ─→ parser.js         53 行 Node 适配层：只保留 extractText
```

- 小程序无法 `require` 到 `miniprogram/` 之外的目录，所以核心文件必须在两端各放一份。
- 固定为「**一份真源 + 单向同步**」：改 `legacy/cloudfunctions/generateSet/parser-core.js`，然后跑 `node tools/sync-parser.js` 同步到 `miniprogram/utils/parser-core.js`。
- **同步脚本内置护栏**：核心出现 `require` / `Buffer` / `process` / `__dirname` 就直接拒绝同步（否则真机必崩）。护栏会先剥掉注释再检查——早期版本没剥注释，把文件头里"不要引入 Buffer"这句说明文字本身判成了违规。
- `_smoke/parser-core.test.js` 在脚本护栏之外再加三层：**两份拷贝逐字节一致**、**护栏自身的回归**（注入违规必须被拦住、注释不得误报）、以及**用子进程把 `Buffer`/`process` 置为 `undefined` 后实跑一遍解析**，验证"零 Node 全局"确实成立。

这样"改一处、两端生效"，不存在两份实现慢慢跑偏的问题。

### 5.3 文件导入链路

```
wx.chooseMessageFile
   → tempFiles[0].path        （本地临时文件，随时会被回收，不能长期依赖）
   → 校验类型 / 大小
   → FileSystemManager.copyFileSync(temp, USER_DATA_PATH/q_source/xxx)
                              （转成本地用户文件：可写、可自定义命名、持久）
   → 建索引（storage）
```

关键点：**临时文件必须拷进沙箱**。官方明确"本地临时文件产生后，仅在当前生命周期内保证有效，重启之后不一定可用"，直接存路径的话下次打开就失效了。

### 5.4 端上解析的能力边界

| 类型 | 端上能否解析 | 原因 |
|---|---|---|
| `txt` / `md` / `json` / `csv` | ✅ | 纯文本，`readFileSync(path, 'utf8')` 即可 |
| `docx` | ❌ | docx 是 ZIP 容器，要解压出 `word/document.xml` 再剥标签。小程序端没有 ZIP 库，且无法在运行时装 Node 依赖 |
| `pdf` | ❌ | 要解析 PDF 对象结构 + zlib 解压缩流。`pdf-parse` 依赖 Node 的 `Buffer` / stream，端上无可移植方案 |

处理方式：**分而治之**——把这两件事挪到电脑上做一次。

`tools/to-txt.js`：

```bash
cd tools && npm install                 # 只需一次
node tools/to-txt.js book.pdf            # 单文件
node tools/to-txt.js ./raw ./txt         # 整目录批量
```

依赖由 `tools/package.json` 自己声明（`pdf-parse` / `mammoth`），**与其他目录解耦**；找不到时会退回 `legacy/` 里旧环境已装好的依赖作为兜底。转换会把行尾统一成 LF、去掉 BOM，与端上保持一致。

对用户来说完整链路是：**电脑转 txt → 发到微信 → 小程序导入 → 生成题库**。转换只需做一次。

### 5.5 交互上的两处堵漏

- 文件库导入时类型不合就**当场提示**，"仍要保存"还是"去电脑转换"由用户决定，不让他走到生成题库才发现失败。
- 生成向导里选到不可解析的文件会**提前拦截**并给出指引，而不是等到点"生成"才报错。

## 6. 兼容性与限制（如实列出）

| # | 限制 | 影响 | 应对 |
|---|---|---|---|
| 1 | **无法从任意位置选文件** | 手机端必须先发到聊天 | 见 §4.4 三条路径；PC 微信已相对方便 |
| 2 | **PDF / docx 端上不可解析** | 直接导入这两类只会保存、不能生成题库 | `tools/to-txt.js` 电脑预处理 |
| 3 | **沙箱共 200MB** | 约 100 本；超出后写入抛错 | 已在文件库页显示占用；`store.storageStats()` 可查；`localdb.cleanOrphans()` 清孤儿文件 |
| 4 | **storage 10MB / 单 key 1MB** | 明细写 storage 会失败 | 架构上已规避：只有索引进 storage |
| 5 | **数据不跨设备、不跨微信账号** | 换手机 / 换号数据不迁移 | 这是"去云"的必然代价。可后续加"导出题库 JSON → 手动搬运" |
| 6 | **用户清缓存 / 清理小程序数据即丢失** | 本地用户文件的清理时机"跟代码包一样" | 与源文件同因；建议保留一份源 txt |
| 7 | **大数据量端上解析耗时** | 单本约 40~80ms（实测 5 本合计 237ms） | 已用 `setTimeout` 让 loading 有机会渲染；无需 worker |
| 8 | **写入是同步的，会短暂阻塞** | 单次写 1.6MB JSON 有可感知停顿 | 只在生成/删除时发生，可接受；量大可改 `writeFile` 异步版 |
| 9 | **`wx.chooseMessageFile` 需基础库 ≥ 2.5.0** | 低版本无法导入 | `app.js` 启动时自检本地存储；建议在项目配置里限制最低基础库 |
| 10 | **原有云端数据不会自动迁到本地** | 之前上传到云的题库在新版里看不到 | 云函数保留未删；如需迁移可写一次性迁移脚本 |

## 8. 遗留与后续可选项

1. **H5 版**：真正做到"任意位置选文件 + 回写源文件"，解析引擎可直接复用（见 §4.4 B）。
2. **题库导出/导入 JSON**：解决"数据不跨设备"和"清缓存即丢失"，实现成本低。
3. **docx 端上解析**：理论上可打包一个纯 JS 的 inflate 实现 + 解析 `word/document.xml`，但会显著增加包体，且 PDF 依然无解 —— 收益有限，暂不建议。
4. **云端数据迁移脚本**：把旧云库里的题库一次性搬到本地。
